# Selection resolver proof pilot

This manually invoked pilot checks the production resolver's rule: an explicit branch
selection determines the result, including unavailability; an available base
cannot replace a missing explicit selection. It is not a proof of the Hub as a
whole. It adds no CI job, file watcher, Git hook, or proof requirement for pushing,
merging or deploying. Ordinary Rust development and release checks are unchanged.

## Source boundary

Production `execution/selection.rs::instance` calls
`execution/selection/kernel.rs::resolve` and maps its typed failures to the existing
public error labels. The standalone `rust` crate imports that **same file** using
`#[path]`. It has its own workspace and no dependencies, so Charon does not need to
translate the Hub's networking, database, SDK or cryptography dependencies.

The shared kernel performs both branch choice and the complete zero/one/multiple
matching scan. The production adapter has no alternative fallback decision.
The existing Hub selection scenario covers concrete registration/error mapping;
the standalone Rust regression is only a quick extraction-package check.

## Regeneration and checking

Run this workflow when verification is explicitly requested. An earlier proof
remains evidence for its recorded source bytes; continued Rust development does
not automatically rerun it.

Use the matching `charon` and `aeneas` executables on `PATH`; Charon also needs its
matching `charon-driver` and Rust toolchain. From this directory:

```sh
cargo test --locked --manifest-path rust/Cargo.toml
cd rust
RUSTUP_TOOLCHAIN=nightly-2026-09-17 charon cargo --preset=aeneas
cd ..
aeneas -backend lean -dest . rust/hub_selection_proof.llbc
lake build
lake env lean SelectionProof.lean
```

`HubSelectionProof.lean` is generated by Aeneas and must not be hand edited.
`SelectionProof.lean` contains the handwritten specification and proofs. Its
`#print axioms` commands expose the proof dependencies; no `sorry` or custom
unproved axioms are permitted. Rebuilding only old Lean output after changing Rust
does not validate the changed Rust: always regenerate from Charon first.

## Semantic mutation experiment

Run this only in an exclusive disposable source snapshot, never while another
process validates the same files. From the repository root:

```sh
git apply proofs/selection/fallback-mutant.patch
cargo check --locked --manifest-path proofs/selection/rust/Cargo.toml
```

The patch changes only the production kernel: on a missing explicit branch it
serves a unique base if available. It is legal Rust and introduces no recursion.
Repeat the Charon, Aeneas and Lean commands above **without changing the proof**.
Compilation and extraction must succeed; the universal proof must fail. A parse
error or failed extraction is not a successful semantic mutation experiment.

Restore the source and repeat the full chain, which must pass again:

```sh
git apply -R proofs/selection/fallback-mutant.patch
```

Keep separate baseline, mutant and restored logs, source/generated/proof hashes,
tool versions, exit statuses and `#print axioms` output. The mutation is an
experiment, not an alternative production behavior.

## Scope and trust

The target theorems quantify over branch/deployment types, arbitrary served slices,
explicit selections and base choices. They distinguish the production result from
the model's outer Rust panic/failure/nontermination outcomes:

- `explicit_selection_ignores_base`: universal equality of the complete result
  for any two bases, without assuming successful comparison or lookup.
- `missing_selection_is_unavailable`: if the generated scan successfully returns
  `Missing`, the resolver returns the typed selected-missing error.
- `missing_selection_does_not_fall_back_to_available_base`: the same result even
  when the generated scan finds a unique available base deployment.

The latter two theorems assume the generated scan's classification. They do not
prove that the scan terminates, avoids panic, or returns `Missing` from a
mathematical absence predicate over the input slice. The scan is extracted from
the production source, but its full correctness is outside these three theorems.

The trusted chain includes the Rust compiler/Charon MIR extraction, Aeneas
translation and standard-library models, Lean's kernel, and the mapping
from the production source to the extraction crate. The generic branch comparison
is an explicit input to the generated model; interpreting it as mathematical
equality would require a comparison-law assumption. These three structural
theorems need no such law.

Lean's elaborator and tactics construct proof terms; its kernel checks those
terms. Extraction failure is a failed pipeline stage, not an outcome admitted by
the resolver theorems.

This pilot does not verify registration gathering, branch string parsing, hashing,
HTTP authentication, current authorization, captured Task routing, PostgreSQL,
OpenShell, concurrency, the compiler's native machine-code output, or the complete
Hub binary. Those remain covered by their existing tests and qualification.

Measured pilot outcomes and the compact historical qualification receipt are in
[RESULTS.md](RESULTS.md). Raw run logs, tool caches and temporary snapshots are
local artifacts, not committed package inputs.

## Production regression check

The builder should also run the existing focused Hub scenario
`a_selection_routes_its_branch_and_never_falls_back` using the repository's normal
test environment. Full Mac/Linux `docker build --target check .` remains the normal
requirement before any production publication; this pilot is not a replacement.
